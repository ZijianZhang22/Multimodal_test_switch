## 目前不能从仓库直接确认什么

根目录历史文档包含多轮准确率、位置效应、probe 和 patching 的报告。当前已检查的 main 文件树中没有相应原始预测与状态产物，因此这些数值保留为历史报告，不作为本次复现结果。

benchmark 的代码存在不代表完整实验已经完成。Pod 上的中途输出、局部样本结果和完整配对结果需要分别标注。尤其不能把某个未完成子集的分数作为官方 benchmark 成绩。

## 统一记录建议

每次运行保存：commit、数据版本、样本 ID / seed、caption 模型及缓存、QA 模型、prompt、解码设置、token 上限、硬件和运行命令。使用独立结果目录；目前不同 runner 的 resume 检查能力不同，不能默认验证全部配置一致。

每组结果至少报告：

| 维度 | 应报告内容 |
|---|---|
| 准确性 | 评分器、总样本、完整配对样本、每条件准确率与 paired flips |
| 开销 | input / output / thinking 指标定义，均值和中位数；是否含 final / 特殊 token |
| 截断 | 每条件 cap 数、终止方式、完整配对且无截断子集 |
| 信息保真 | caption 是否漏掉答案所需事实；不能将 caption 差异自动归为推理能力差异 |
| 统计单位 | 同一问题的条件配对；toy 中检查重复关系链，避免将重复样本当独立泛化证据 |
| 结论范围 | toy / benchmark、模型版本、prompt、预算与样本选择策略 |

caption 生成成本应在端到端效率结论中单独计入；只比较 QA output tokens 回答的是下游生成开销。

## 哪些结论暂时不宜写成定论

- “多模态 switching 必然导致性能下降”。
- “更多 CoT 一定更准确”或“更少 tokens 就是更高效”。
- “失败已定位于视觉 encoder”。
- “所有图文替换与多任务 compression 都来自同一个机制”。

这些是待竞争检验的假设，而不是当前目录结构能够证明的事实。
